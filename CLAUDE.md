## Commands

```bash
npm run dev      # Start Vite dev server
npm run build    # Production build (outputs to dist/)
npm run lint     # Oxlint (config in .oxlintrc.json)
npm run preview  # Serve the production build
```

There is no test suite.

## What this is

Phase 1 MVP of the Sabha Mandal Attendance & Event Registration System — a mobile-friendly React app for marking event attendance against a participant roster imported from Excel, with a fallback registration flow for people not in the roster. Requirements live in [attendance-system-prd.md](attendance-system-prd.md) and [attendance-system-brd.md](attendance-system-brd.md); consult them before changing workflows or business rules. `test_roster.csv` is a sample import file.

Domain terms: a **sabha/mandal** is a class/group, a **balak** (participant) is an attendee, and a **karyakar** is the person responsible for a group.

## Architecture

React 19 + Vite (JavaScript, no TypeScript). There is **no router**, and the data layer is **dual-mode**: with `VITE_SUPABASE_URL`/`VITE_SUPABASE_ANON_KEY` set (see [SETUP-BACKEND.md](SETUP-BACKEND.md)) the app runs in cloud mode — Supabase Postgres via a write-through sync layer ([src/lib/cloudSync.js](src/lib/cloudSync.js)), realtime cross-device refresh, Supabase email/password auth with a `profiles` roles table, and RLS enforcing the D4 matrix server-side ([supabase/schema.sql](supabase/schema.sql)). Without them it is the original client-only sandbox. React state stays the synchronous source of truth in both modes — views never await data — and most mutations flow through `saveToStorage`, which mirrors to localStorage (offline cache) and, in cloud mode, reconciles the corresponding table. **Concurrently-written rows are the exception**: `markPresent`, `undoAttendance` and `publicSelfCheckIn` use the row-level `insertRow`/`deleteRow` helpers instead, because a full-table reconcile prunes rows this device has not received yet and silently deletes other volunteers' work. Check `isCloudMode` from [src/lib/supabase.js](src/lib/supabase.js) before adding mode-specific behavior:

- **Persistence** is `localStorage` under `ams_*` keys, managed entirely by [DbContext.jsx](src/context/DbContext.jsx). It seeds mock data on first load and exposes the whole "database API" via `useDb()`: participant fuzzy search (`queryParticipants`, score-ranked), Excel/CSV import upserting on name + guardian phone (`importExcelData`), event CRUD, attendance marking with duplicate/closed-event guards (`markPresent`, `undoAttendance`), registration, and admin wipe/reset. Every mutation writes to localStorage and appends an audit log entry via `addAuditLog`.
- **Auth** is dual-mode, in [AuthContext.jsx](src/context/AuthContext.jsx). Sandbox is mock-only: preset usernames (`admin`, `coordinator`, `attendance_vol`, `reg_vol`) and any write-in name as a custom user, no passwords. Cloud mode is real Supabase email/password with the role read from `profiles`. `hasPermission(requiredRole)` implements the hierarchy (Admin overrides all; Coordinator subsumes Registration Volunteer; anything else is base level — so **every signed-in user can mark attendance**, which is why Registration Volunteer covers both marking and registering). In cloud mode new accounts are created **disabled** and an admin activates them; `addCloudUser` creates real logins from Admin Control using a `persistSession: false` client so the admin's own session survives.
- **Navigation** is a `view` string in [App.jsx](src/App.jsx) switched over the components in `src/views/`; [Layout.jsx](src/components/Layout.jsx) renders the nav, filtering items by `hasPermission`. The one URL-driven route is the public shared registration link (`?view=shared-registration`, `eventId` optional), which bypasses login and renders `SharedRegistration` directly. Without an `eventId` it targets whichever event is currently `Active`, so one permanent link never goes stale.

Key business rules enforced in DbContext: events have `Draft`/`Active`/`Closed` statuses; attendance cannot be marked or undone on a `Closed` event — **except** by an Admin passing `{ allowClosed: true }` to `markPresent`/`undoAttendance`, which is how a closed event's roster is corrected from Reports (events auto-close past their end time and an expired one can never be reopened, so without this a missed mark is permanent); note this rule is client-side only, as `attendance_insert`/`attendance_delete` never inspect event status for a signed-in user; a participant cannot be marked present twice for the same event (enforced server-side too, by a `unique (event_id, participant_id)` constraint that arbitrates between concurrent devices); participant identity is keyed on **name + guardian phone**, not phone alone, because siblings share a guardian's number (helpers in [src/lib/participantIdentity.js](src/lib/participantIdentity.js)); registering a new participant with an active `eventId` also marks them present; and `publicSelfCheckIn` creates an `approved` participant and marks them present in one step from the shared link.

Karyakars are stored as `{ name, sabha }` objects mapped to their sabha (legacy string arrays in localStorage are auto-migrated): registration forms auto-select the karyakar from the chosen sabha, so never present them as two independent dropdowns.

Sabhas are likewise `{ name, area }` objects, not strings (`migrateSabhasList` upgrades legacy string arrays). **Views want `sabhaNames` from `useDb()`, not `sabhas`** — that derived string array is what every dropdown and `includes` check uses. An **area** groups several mandals for reporting only; events are still scoped to one sabha or `All Sabhas`. A participant's `sabha` is free text and need not exist in the lookup, so always resolve it through `areaOfSabha(name)`, which falls back to `Unassigned` rather than dropping the row from a report.

Participants carry a lifecycle `status`: `approved` (on rosters/reports), `pending` (review queue; searchable at the desk with a badge), `rejected`, `linked` (merged/linked to another record via `linkedToId`), `archived` (retention removal). Legacy `pendingReview` flags auto-migrate on load. Only `approved`/`pending` records are "active" — searches, duplicate checks, and import upserts must filter to those. Lifecycle transitions go through the dedicated DbContext actions (`approveParticipant`, `mergeParticipants`, etc.), which enforce the role matrix from [phase-0-decisions.md](phase-0-decisions.md) D4 — as do all other mutations. Note the shared link no longer produces `pending` rows — it creates `approved` participants directly, because Reports only counts `approved` on rosters. User accounts live in localStorage (`ams_users`) in sandbox mode, or the Supabase `profiles` table in cloud mode, both managed via `AuthContext` (`addManagedUser`, `addCloudUser`, `setManagedUserEnabled`, `setManagedUserRole`).

Sorting: [src/lib/tableSort.js](src/lib/tableSort.js) holds `compareValues` / `sortRows` / the `useTableSort` hook, and [SortableTh.jsx](src/components/SortableTh.jsx) is the clickable `<th>`. Call `useTableSort()` **once per table** (never share one between tables) and **declare it with the first state cluster** — Reports builds `reportRoster` far above its second cluster, so a later `const` is a temporal-dead-zone ReferenceError. Apply `.sorted()` at the array-definition site, not in the JSX: the Excel exports and QR badge sheet iterate those same arrays, which is how they inherit the on-screen order. Give each array a meaningful base sort — `sortRows` is stable, so the base doubles as the tiebreak.

Styling is plain CSS in [src/index.css](src/index.css) (no CSS framework). Brand colors live in [src/theme.css](src/theme.css) — the only place to change primary/secondary colors (current palette: Kesari saffron & maroon); `index.css` derives `--accent*` from those theme variables, so never hardcode accent hex values in components.

i18n: user-facing strings on public/volunteer surfaces go through `t('key')` from [src/i18n/LanguageContext.jsx](src/i18n/LanguageContext.jsx) with English + Gujarati dictionaries in [translations.js](src/i18n/translations.js) (missing keys fall back to English). The app is an installable PWA — [public/sw.js](public/sw.js) caches the shell in production builds only (never registered in dev). QR check-in: receipts and printable badges encode the participant ID via [QrCode.jsx](src/components/QrCode.jsx); the desk scanner uses the browser BarcodeDetector API with manual ID entry fallback.
